# Tiny Diplomacy Protocol Crate — Testing Specification

- **Status:** Baseline test requirements
- **Date:** 2026-10-02
- **Protocol:** `tiny-diplomacy/v0-press`
- **Companion:** `Tiny_Diplomacy_Protocol_Baseline_Requirements.md`

## 1. Purpose and scope

The protocol tests establish that the model can observe a decision, generate tokens incrementally, and submit exactly the intended legal typed response. They must work without a trained model, Candle, or GPU.

The central invariant is:

> Given a valid fixed decision snapshot and sufficient response capacity, every completed response generated through the allowed-token masks parses successfully and passes authoritative engine validation.

That invariant has two sides. Masks must exclude invalid continuations, and they must preserve all legal canonical continuations within the configured budget. A decoder that permits only HOLD is safe but incomplete.

This specification describes required tests, not tests already implemented or executed. File organization and test names below are suggestions; `../../docs/game-spec.md` and `../../docs/protocol.md` remain authoritative.

## 2. Test authority and independence

Use the game engine as the authority for game-action legality and the press engine as the authority for press semantics. Test the protocol's translation and enforcement of those rules; retain comprehensive adjudication and scheduling tests in their owning crates.

Avoid circular assertions. Encoder/decoder round trips alone can pass when both share the same mistake. Combine:

- Hand-authored expected token sequences and masks.
- Typed expected actions constructed directly from engine types.
- Engine validation of parsed results.
- Bounded independent enumeration of canonical legal responses.
- Property tests and complete-game integration traces.

Expected golden files must not be generated by the production encoder during the test. Review intentional changes to them as protocol changes. Do not automatically bless a failing fixture.

## 3. Fixture conventions

Every fixture identifies acting power, phase/year, units, center owners, generation mode, relevant press state, and response/context budgets. State whether it is reachable through ordinary play or a deliberately constructed valid engine state. Negative state fixtures must say which precondition they violate.

Keep geography explicit. Coordinates use orthogonal adjacency. In particular, B3 cannot support entry into C2: those cells are diagonal. Use BLUE at C3 to support RED moving B2 to C2.

Suggested reusable fixtures:

| ID | Setup and purpose |
| --- | --- |
| F-INITIAL | Spring, year 1; GREEN A1, RED B5, YELLOW D2, BLUE E5; original homes owned; B2/C3/C6/E3 neutral |
| F-SINGLE | RED B2; no other armies; nonterminal movement decision; simple exact masks |
| F-SUPPORT | RED B2 and BLUE C3; both adjacent to C2; legal cross-power support to move |
| F-HOLD-SUPPORT | RED B2 and BLUE B3; adjacent armies; legal support to hold |
| F-FRIENDLY | RED B2 and RED C2; tests legal submission into friendly occupancy |
| F-ZERO | Acting power has no armies; game remains nonterminal |
| F-BUILD | Winter; RED owns empty B5; center count exceeds army count |
| F-DISBAND | Winter; RED armies A2/B2/C2 and one owned center; two required disbands |
| F-PROPOSAL | Eligible BLUE activation with an outstanding RED-to-BLUE proposal |
| F-PRIVATE | RED/BLUE private exchange, observed separately as each of the four powers |

Fill all unspecified ownership and calendar values explicitly in code. Never let builder defaults accidentally make a fixture terminal or change its adjustment delta.

## 4. Vocabulary and compatibility tests

| ID | Requirement |
| --- | --- |
| TOK-01 | Inventory has exactly 82 unique symbols and 82 unique IDs |
| TOK-02 | Every token converts symbol → ID → symbol without loss |
| TOK-03 | Exact ID assignments match a reviewed, checked-in manifest |
| TOK-04 | Unknown integer IDs and textual spellings produce explicit errors |
| TOK-05 | `EOS`, `PAD`, `UNK`, punctuation, and ellipses are not semantic tokens |
| TOK-06 | Debug whitespace does not alter tokenization where text parsing is supported |
| TOK-07 | The artifact-loading boundary rejects incompatible vocabulary/version metadata |
| TOK-08 | Context-only tokens are rejected in every generated response mode |

TOK-03 uses the frozen table in protocol Section 1.8: IDs 0–11 controls, 12–17 powers/cell values, 18–20 phases, 21–30 years, 31–37 game actions, 38–45 press tokens, and 46–81 row-major locations. Its canonical manifest SHA-256 is `1f21b70055bc131316ea17152c7be4928e5d0e82fef018b88ad950eee0ae83e7`. Hand-author the fixture; do not derive it from enum iteration at runtime. If checkpoint loading belongs to another crate, TOK-07 is an integration obligation there.

## 5. Observation serialization

For F-INITIAL, hand-author a complete symbolic golden vector for each acting power. Convert it using the independently checked vocabulary table when comparing numeric IDs.

Assert exact contents, not only length:

- Header is `BOS <power> SPRING YEAR_1`.
- All 36 location/occupant pairs appear in row-major order.
- Initial occupied cells and all 32 empty cells are correct.
- Centers appear as `A1 B2 B5 C3 C6 D2 E3 E5`, each with its actual owner.
- The supplied prompt ends in the requested legal generation marker.
- A base observation without diplomatic context has exactly 95 tokens.

Add Autumn, Winter, years 1 and 10, captured-but-empty centers, occupied non-centers, and zero-army observations. A captured center's persistent owner must not be inferred from its current occupant.

Reject unsupported years, incompatible mode/phase combinations, and terminal decisions. Winter 9 is representable, but the game terminates after Autumn 10 and must never produce a Winter 10 decision. Test invalid input states at the boundary that actually accepts them; do not bypass Rust type invariants merely to manufacture impossible values.

Rebuild equivalent states with different collection insertion orders and require identical output. If observation decoding exists, compare only the information actually encoded; it cannot reconstruct hidden press state.

## 6. Movement response tests

For each valid response, assert strict parsing into the expected typed order set, canonical re-encoding, and successful engine legality validation.

| ID | Case | Expected result |
| --- | --- | --- |
| MOV-01 | F-SINGLE: `B2 HOLD END` | Accept |
| MOV-02 | F-SINGLE: `B2 MOVE C2 END` | Accept |
| MOV-03 | RED B2/BLUE B3: `B2 SUPPORT B3 HOLD END` | Accept |
| MOV-04 | BLUE acting at C3, RED B2: `C3 SUPPORT B2 MOVE C2 END` | Accept |
| MOV-05 | Move B2 to diagonal C3 or distant F6 | Reject |
| MOV-06 | Source belongs to another power or is empty | Reject |
| MOV-07 | Referenced supported army does not exist | Reject |
| MOV-08 | Supporter cannot reach supported destination | Reject |
| MOV-09 | Supported army cannot reach supported destination | Reject |
| MOV-10 | Omitted, duplicated, or out-of-order source | Reject |
| MOV-11 | F-ZERO: `END` | Accept |
| MOV-12 | `END` before all owned armies have orders | Reject |
| MOV-13 | Move into friendly occupancy, with all required orders present | Accept submission; leave outcome to adjudication |

Independently test that support remains legal when the other army later submits a different order, and that a legal move remains legal when it later bounces. Future success must not be a parsing or masking prerequisite.

Adding, removing, or changing commitments while holding board state fixed must leave the movement masks unchanged for the same prefixes and token budget. Include an explicit legal order that breaks a recorded promise.

## 7. Winter response tests

Cover all adjustment branches and exact completion behavior:

| ID | Case | Expected result |
| --- | --- | --- |
| WIN-01 | Delta zero: `NONE END` | Accept; alternative adjustment forms rejected |
| WIN-02 | Positive delta and eligible home: `BUILD B5 END` | Accept for RED |
| WIN-03 | Positive delta: `WAIVE END` | Accept, whether or not a build is available |
| WIN-04 | Home occupied or no longer owned | Build rejected; waiver remains possible |
| WIN-05 | Build on captured enemy home or ordinary cell | Reject |
| WIN-06 | Delta greater than one | At most one build; no repeated waiver tokens |
| WIN-07 | F-DISBAND: `DISBAND A2 DISBAND C2 END` | Accept |
| WIN-08 | Too few/many disbands, duplicate location, wrong owner | Reject |
| WIN-09 | Disbands emitted in descending location order | Reject as noncanonical |
| WIN-10 | Mixed builds and disbands, voluntary disband at delta zero | Reject |

Test sorted-disband lookahead: with A2/B2/C2 and two removals required, C2 must not be offered as the first disband location because no greater second location remains. Syntax-only masking would otherwise create a dead end.

## 8. Press response tests

Create eligible activations through the press engine where possible. Set proposal state using legal prior messages rather than directly forging internals.

| ID | Case | Expected result |
| --- | --- | --- |
| PRS-01 | `END` | Silence; no message budget charged on submission |
| PRS-02 | Public and private forms of each speech act | Preserve visibility, recipient, actor, and terms |
| PRS-03 | Message addressed to sender | Reject |
| PRS-04 | PROMISE term names another power | Reject |
| PRS-05 | REQUEST term names someone other than recipient | Reject |
| PRS-06 | PROPOSE term names a third party | Reject |
| PRS-07 | Empty PROMISE/REQUEST/PROPOSE bundle | Reject |
| PRS-08 | Two contradictory orders for one army | Reject |
| PRS-09 | `AVOID` location currently occupied by its actor | Reject |
| PRS-10 | Same bundle promises entry into X and AVOID X for that actor | Reject |
| PRS-11 | Same bundle promises support for entry into X and AVOID X | Reject |
| PRS-12 | ACCEPT/REJECT with no incoming proposal | Reject |
| PRS-13 | Only reverse-direction proposal exists | Reject acceptance/rejection of nonexistent incoming proposal |
| PRS-14 | New proposal supersedes old one in the same direction | Parsed acceptance submits against the current proposal |
| PRS-15 | Public acceptance of a private proposal | Permit under current semantics; visibility handling remains authoritative in press engine |
| PRS-16 | Exhausted send budget, eligible activation | Only `END` reachable |
| PRS-17 | Winter, closed phase, wrong active power | Reject decision/session or submission at its owning boundary |
| PRS-18 | Repeat a rejected proposal in a later eligible activation | Permit while budget remains |

Term order is lexicographic over complete token-ID encodings, and exact duplicates within one message are rejected. Test both rules directly. Do not infer a ban on contradictions across separate messages from the ban within one bundle.

## 9. Parser strictness and error behavior

For valid examples of every response form, derive targeted invalid variants: remove an operand, remove `END`, append a token after `END`, insert an unrelated control token, substitute a wrong token category, and exchange canonical source order. Assert rejection for variants that actually become invalid.

The parser consumes the generated suffix. Supplying `ORDERS`, `ADJUST`, or `PRESS` as its first generated token must not be confused with parsing the full prompt.

Check stable error categories, mode, and token position where defined. Avoid asserting exact prose messages. Parsing or masking must not alter the game, consume an activation, mark inboxes read, create commitments, or increment message counts.

A failed incremental `push` leaves decoder state unchanged: capture its prefix and mask, submit a forbidden token, then verify both remain identical and a valid continuation still succeeds. Repeated parsing of the same input yields the same result.

## 10. Exact incremental-mask tests

For F-SINGLE with ample response capacity and no other armies:

| Generated prefix, excluding `ORDERS` | Exact allowed set |
| --- | --- |
| Empty | `{B2}` |
| `B2` | `{HOLD, MOVE}` |
| `B2 MOVE` | `{A2, B1, B3, C2}` |
| `B2 HOLD` | `{END}` |
| `B2 MOVE C2` | `{END}` |
| `B2 HOLD END` | Terminal; no further token accepted |

SUPPORT is excluded after B2 because no supported army exists. Repeat with corner and edge armies to test adjacency boundaries.

For a press activation with zero send capacity, the initial mask is exactly `{END}`. For F-PROPOSAL, verify ACCEPT and REJECT availability after the correct visibility/recipient prefix, and their absence when only the opposite-direction proposal exists. After ACCEPT or REJECT, only END is valid.

Test every operand position of support and press terms, not only initial action selection. A token that is locally grammatical but admits no complete legal continuation must be excluded.

## 11. Bounded exhaustive oracle

For small fixtures and explicit finite response budgets, construct an independent set L of all canonical legal complete suffixes within that budget. Build candidates using simple test-only grammar enumeration and direct typed engine validation. Do not generate L by walking the production mask, and do not rely solely on the production parser to label candidates legal.

For each proper prefix p of members of L, compute:

```text
expected_next(p) = { t | some response in L begins with p followed by t }
```

Require exact equality with the production mask. For complete suffixes, require terminal state. An empty L must produce an explicit impossible-decision/budget result rather than an all-false mask passed to sampling.

This checks soundness, completeness, correct END placement, and absence of reachable dead ends within the tested domain. Include one-army movement, small support arrangements, mandatory disbands, and press bundles bounded by token length. Record enumeration bounds; do not describe bounded coverage as proof over every possible game.

## 12. Response and context budgets

Budgets count generated tokens including END. For F-SINGLE, two tokens are insufficient, three allow only `B2 HOLD END`, and four also allow moves. Verify these exact boundary cases.

For each grammar branch, test minimum completion length minus one, exactly the minimum, and one above it. Longer branches must disappear before consuming tokens needed for mandatory completion. No path may force an incomplete term to terminate.

Context tests count supplied prompt plus the entire reserved generated suffix against the configured limit, initially targeting 512 tokens. Test exact fit, one-token overflow, longest-contiguous-history-suffix selection, and required-state overflow. Do not silently truncate the board, center state, a structured record, inbox contents, proposals, or commitments. A newer record that does not fit prevents selection of older records.

Distinguish send-message budget from token budget: END costs a response token but no sent message. A long message still consumes one send slot. Zero send capacity does not make a legitimate silent activation unrepresentable.

## 13. Privacy and diplomatic-context tests

Add full golden observations using the fixed `DIPLOMACY INBOX PROPOSALS COMMITMENTS HISTORY` section order. Include public messages, sent/received private messages, outstanding proposals, active commitments, and history. Verify `BOS`/`END` record boundaries, sender identity, phase/year, visibility, counterparty, and separation between current state and expired history.

Verify section-specific ordering: inbox delivery order, proposals by `(sender, recipient)`, commitments lexicographically by complete token encoding, and history by per-observer visible chronology. Empty sections remain present whenever the diplomatic block is present. Winter observations omit the block.

For RED-to-BLUE private press, RED and BLUE may see the exchange; GREEN and YELLOW must not see its content, existence markers, global sequence gaps, or hidden-state-dependent history selection.

Use paired snapshots with identical public and observer-visible state, fixed observer activation and budgets, and different hidden RED/BLUE exchanges. Require identical GREEN encodings and allowed response masks. Do not compare states where an explicit public acceptance or another authorized disclosure has changed visible information.

Public messages are visible to all powers but trigger an inbox opportunity only for the addressed recipient. Verify this at the integration boundary. Test visibility preservation through parse → submit → filtered view → encode, especially for mixed-visibility proposal/acceptance sequences; expected disclosure follows the press engine's documented rules.

For a public acceptance of a private proposal, uninvolved powers see the acceptance record but not proposal terms, commitment records, or later outcomes. For a private acceptance of a public proposal, uninvolved powers retain the public proposal in eligible history but do not see that it became active. Commitment details are public only when both proposal and acceptance were public.

Changing another power's privately submitted movement orders must not change the current power's movement prompt or mask. Changing the current power's visible commitments may change its prompt, but must not constrain its legal movement choices.

A filtered Rust view alone does not satisfy context serialization tests. Golden token encodings are mandatory.

## 14. End-to-end integration without a model

Build a seeded test driver that picks only allowed next tokens, completes the response, parses it, submits it to the owning engine, and repeats through press, movement, Winter, and terminal outcomes. Use uniform random selection plus scripted traces; random token sampling is not uniform sampling over complete actions.

For every decision, assert:

1. Observation fits its configured capacity or produces the documented explicit overflow.
2. Every nonterminal reachable prefix has a valid continuation.
3. The completed response parses and is engine-valid.
4. Submission produces the same transition as directly submitting the expected typed action to a cloned engine state.
5. No malformed-order fallback was needed for masked generation.

Script traces for a proposal and acceptance, supersession and rejection, silence, exhausted send capacity, fulfilled but bounced movement, and deliberate promise violation. For a four-power press phase with per-power send cap M, sent messages must be at most 4M. Under the specified opening/inbox schedule, activations are bounded above by 4 + 4M; inbox batching can reduce that number. Check this only for ordinary valid responses, separately from any raw-invalid retry policy.

Raw malformed press generation must consume the activation, mark its triggering inbox batch read, deliver no message, create no negotiation state, charge no send-message budget, and perform no automatic retry. The pure parser must remain read-only; test runner behavior separately.

## 15. Property tests, fuzzing, and reproducibility

Generate reachable snapshots by driving legal engine actions from valid starting states. Supplement these with targeted constructed states for rare boundaries. Property tests cover canonical round trips, insertion-order invariance, parser/mask agreement, purity, promise independence, and visibility isolation.

Fuzz arbitrary token arrays and decoder operation sequences. Require no panic, no unbounded loop, explicit errors, and no authoritative-state mutation. Use configured length limits to keep adversarial inputs bounded. Fuzzing input validation complements legal-state generation; it does not replace it.

Every random failure must record seed, protocol version, state fixture, acting power, mode, budgets, generated prefix, actual mask, and expected/engine error. Shrink it where possible and retain the minimal reproducer as a regression test. Keep hidden press details in developer diagnostics, never in model-visible observations.

## 16. Suggested organization and execution gates

| Suggested suite | Scope |
| --- | --- |
| `vocabulary.rs` | Token manifest and conversions |
| `observations.rs` | Golden state/context encoding |
| `movement.rs`, `adjustments.rs`, `press.rs` | Typed responses, legality, and negative cases |
| `masks.rs`, `mask_oracle.rs` | Exact prefixes and bounded exhaustive checks |
| `privacy.rs`, `budgets.rs` | Visibility, context, and termination capacity |
| `integration.rs` | Engine submission and complete phase/game traces |
| `properties.rs` and fuzz targets | Generated states and arbitrary malformed input |

Per-change CI should run deterministic fixtures, bounded oracle cases, integration traces, and a fixed reproducible property-test workload. Longer scheduled/manual runs broaden seeds, state coverage, and fuzz duration. Record their actual workload; no particular test count substitutes for scenario coverage.

The protocol milestone passes when every mandatory case above has evidence, the frozen ID/canonicalization/context fixtures match the authoritative protocol, masks satisfy bounded soundness and completeness checks, and end-to-end runs require no invalid-action fallback. Any proposed change to those fixtures is a protocol-version change, not an automatic test update.
